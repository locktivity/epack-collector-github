# Changelog

## Unreleased

## v0.4.8

- The Not Collected section of `docs/overview.md` is rendered from `docs/surface.yaml`, which gives a verdict to every read operation of GitHub's published Enterprise Cloud API description that the collector's recordings never call, so the list comes from GitHub's description rather than from memory. A new `docs/coverage.md` lists what the collector reads, by area, every operation it leaves out with the reason, and the three calls the collector makes that the sandbox never exercises.

## v0.4.7

- A list is left out with an `invalid_response` gap when GitHub answers it with an item that lacks a field its REST reference requires. That covers an open alert with no `number`, a code scanning alert with no `rule`, a Dependabot alert with no severity, a webhook with no `id`, `active` or `events`, a deploy key with no `id` or `read_only`, a self-hosted runner with no `id` or `busy`, an installed App with no `app_id` or `suspended_at`, a fine-grained token grant with no `id`, `token_expired`, `token_expires_at` or `token_last_used_at`, and a member, owner or outside collaborator with no `login`. Through v0.4.6 such an item counted with a false, zero or empty value, and a person with no login dropped out of the counts.
- The audit log is left out with an `invalid_response` gap when an event has no `action` or `created_at`. Through v0.4.6 an event with no action dropped out of `count_by_category`, and one with no `created_at` had a timestamp of 0.
- The runners, the Actions secrets, the installed Apps, the environments and the GitHub App's repositories are left out with an `invalid_response` gap when a page of their list holds none while fewer than its `total_count` have been read. So are the environments when a repository's list has no `total_count`. Through v0.4.6 the rows read were kept and marked as truncated, the GitHub App counted as installed on only the repositories read, and an environment list with no `total_count` counted 0 environments.
- The repository list is left out with an `invalid_response` gap when a repository in GitHub's GraphQL answer leaves out a field the collector selects, holds null in one GitHub's schema makes non-null, such as a classic rule's `isAdminEnforced`, or the page has no `pageInfo`. So are the member names and the SAML values when their page has no `pageInfo`. A repository whose `diskUsage` is null has `size_kb` left out with an `unsupported` gap. Through v0.4.6 a missing setting read as false, a page with no `pageInfo` ended the list, and a null `diskUsage` left `size_kb` out with no gap.
- A repository's ruleset rules are left out with an `invalid_response` gap when a rule has no `type`, a pull request rule lacks `required_approving_review_count`, `dismiss_stale_reviews_on_push` or `require_code_owner_review`, or a status checks rule has no list of checks. A ruleset's details are left out the same way when a bypass actor has no `actor_type`, or no `actor_id` where GitHub requires one. Through v0.4.6 such a rule read as protection not in place, and an actor with no type left admin enforcement null with no gap.
- A repository's secret scanning, push protection and Dependabot security updates are each left out with an `invalid_response` gap when its `security_and_analysis` block has no status for that setting. Through v0.4.6 a missing status read as disabled.
- The environments are left out with an `invalid_response` gap when a protection rule has no `type`, a required reviewers rule has no `prevent_self_review`, or a wait timer rule has no `wait_timer`. An environment GitHub sends with no `can_admins_bypass` has that value left out with an `unsupported` gap. Through v0.4.6 these read as gates the environment did not have, and `can_admins_bypass` was left out with no gap.
- The SAML values are left out with an `invalid_response` gap when GitHub's answer has no `samlIdentityProvider` field, or lists an identity with no `samlIdentity` or `scimIdentity` field. A null `samlIdentityProvider` still means the organization has no identity provider. Through v0.4.6 a missing provider read as none, and a missing identity field as no linked identity or no SCIM record.

## v0.4.6

- The collector is built on epack v0.11.1.
- The credential values in the access file leave out a fine-grained personal access token that expired, which GitHub lists until its grant is revoked, and a deploy key GitHub disabled, as it does when the organization or its enterprise stops allowing deploy keys. Before, both counted.
- A ruleset's status checks rule counts toward `status_checks_pct` only when it names at least one check, since GitHub's rule has no effect until it does.
- GitHub returns no classic branch protection rule, and no error, to a caller without admin rights on the repository, such as a GitHub App without Administration. When GitHub also hides the repository's `security_and_analysis` block, which it hides from the same callers, the branch protection values a classic rule could change are left out with a `permission_denied` gap. Before, the repository counted as having no classic rule.

## v0.4.5

- In the access file, every member counts as an admin when the members' base permission is admin, since each of them can then change who has access to every repository. Outside collaborators do not get the base permission and are not counted.
- Below the admin base permission, a member can still be an admin through an organization role, such as All-repository admin or a custom role that can administer repositories. The collector does not read organization roles, so `admin_count`, `admin_share_pct`, `local_admin_count`, `local_mfa_admin_count` and `local_admin_mfa_coverage_pct` are left out with a `not_read` gap. The owners still make `admins_present` and `local_admins_present` true. When GitHub withholds the base permission, these values are left out with a `permission_denied` gap.

## v0.4.4

- The collector is built on Go 1.26.11.
- `artifacts/github.access-posture.json` has `root` now. A GitHub organization has no built-in root account, so `root_accounts_present` and `root_access_keys_present` are false and `root_mfa_coverage_pct` is null. From the audit level, `root_account_count` and `root_mfa_account_count` are 0. Before, `root` was left out with an `unsupported` gap. A profile test that applies only when `root.root_accounts_present` is true no longer applies to GitHub.

## v0.4.3

- The collector is built on epack v0.10.5.
- The collector result has `targets` now. They name the organization, at `organization` in `artifacts/github.vcs-posture.json`, and the repositories the run assessed, at `repositories.per_repo` in `artifacts/github.details.json`, with how each was chosen. When a GitHub App is installed on selected repositories, the repositories are `granted`, or `granted_filtered` when patterns also narrow them, since the organization may have others the run never saw. Audit and internal runs write `"per_repo": []` for an organization with no repositories, where they left `per_repo` out before.

## v0.4.1

## v0.4.0

- The collector is built on epack v0.10.0. The detailed artifact moves from `artifacts/github.json` to `artifacts/github.details.json`, the path epack's `ArtifactPath` gives it. A reader of the old path needs the new one
- Each run writes `artifacts/github.access-posture.json`, in the `evidencepack/access-posture@v1` format, and `collect` lists it as `access-posture`. It covers the two-factor requirement, SAML single sign-on, members, owners, machine credentials, and installed GitHub Apps. Below the audit level it holds present flags and percentages, and from the audit level it adds the counts.
- Each run writes `artifacts/github.vuln-scanning.json`, in the `evidencepack/vuln-scanning@v1` format, and `collect` lists it as `vuln-scanning`. It has an entry each for Dependabot, code scanning, and secret scanning, with the scanner's coverage of the in-scope repositories.
- `artifacts/github.vcs-posture.json` no longer has `org_security` or `security_features`, since `evidencepack/vcs-posture@v1` no longer has them. `org_security.two_factor_required` is now `sign_in.mfa_required` in the access file. `security_features.vuln_alerts_pct`, `code_scanning_pct`, and `secret_scanning_pct` are now `coverage_pct` on the vulnerability file's `dependabot`, `code_scanning`, and `secret_scanning` entries. Their repository counts are now each entry's `scanned_resource_count`. The detailed artifact keeps `access_control` and `security_features` as they were.
- In the access file, members are the organization's members and outside collaborators, and outside collaborators count as external members. SSO members are the members with a linked SAML identity. Admins are the organization's owners. Whether the organization requires SAML single sign-on is not available from GitHub's organization API. So every member and owner counts as able to sign in without SSO, including those linked to SAML.
- MFA in the access file comes from GitHub's list of members without two-factor authentication and its list of outside collaborators without it. The collector reads the second list from `GET /orgs/{org}/outside_collaborators?filter=2fa_disabled`, with the members permission the member list already needs. It skips that call when the organization has no outside collaborators. At the internal level, an outside collaborator's row in the detailed artifact's `members.per_member` now has `two_factor_enabled` too.
- The access file's credentials are the fine-grained personal access tokens approved for the organization and the deploy keys of the in-scope repositories. A deploy key never expires, and a read-write deploy key has write access. A token counts as never expiring when it has no expiry date, and as unused when it was never used or not in the last 90 days. Classic tokens are not counted. No token or deploy key counts as unrestricted. A token has only the permissions and repositories it was given, and a deploy key works on one repository. The rotation values count the deploy keys created more than 90 days ago. GitHub's list of token grants has no creation date, so the rotation values are left out with an `unsupported` gap when the organization has approved any fine-grained token.
- In the access file, `connected_apps` counts only the installed GitHub Apps that are not suspended. A suspended App has no access to the organization. When the list of installations stops at 10,000, `app_count` is left out with a `too_large` gap.
- Some access values have no data in GitHub and are left out with an `unsupported` gap. They are the inactive member values and `root`. GitHub reports whether an organization requires SAML single sign-on only to enterprise owners, in the GraphQL field `EnterpriseOwnerInfo.samlIdentityProviderSettingOrganizations`. The collector does not read it, so `sign_in.sso_required` is left out with a `not_read` gap.
- In the vulnerability file, the Dependabot and code scanning entries count the open alerts by severity and the overdue ones. A finding is overdue when it is rated critical and was created more than 30 days ago, or rated high and created more than 90 days ago. A code scanning alert takes its rule's `security_severity_level`, and an alert from a rule that is not a security query is not counted. Secret scanning alerts have no severity, so those values are left out with an `unsupported` gap.
- A trust run now lists the members, owners, outside collaborators, deploy keys, installed Apps, fine-grained token grants, and open code scanning and Dependabot alerts for the new files. Each list is read only when its file is collected. The token grants need the organization Personal access tokens permission (read). A missing permission leaves out only the values from that list, with a gap.
- A new GraphQL query reads the organization's `samlIdentityProvider` and its members' external identities. It needs the members permission, or `read:org` for a classic token. An organization with no SAML identity provider, as on any plan below GitHub Enterprise Cloud, has `sign_in.sso_configured` false. The collector now also reads each identity's SAML NameID and the login of the member it belongs to. From the audit level, each member's row in the detailed artifact's `members.per_member` holds the NameID as `saml_name_id`, so an access review can match members to identity provider accounts. The collector reads the SAML identities when the run writes the access file or the detailed artifact.
- Each operation in the collector result now has a `permission` field with the permission its call needs, such as `members:read`. As before, `missing_permission` is set on a denied call's gap only when the GitHub App lacks that permission.
- The collector gives an `x-epack-method` sentence for each value of the access and vulnerability files in `docs/schema/methods.json`. The coverage values and `sign_in.mfa_required` copy detailed values and use their sentences.
